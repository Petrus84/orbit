O que é o Orbit Dashboard
Plataforma SaaS de analytics de Instagram para e-commerce e agências brasileiras, construída em Next.js + TypeScript + Supabase (schema orbit). Dois clientes reais em operação: @cpimportstore (e-commerce de gadgets/casa/cozinha) e @eupetruchio84 (fitness).
A regra de arquitetura central é: src/types/orbit.ts é a fonte única de verdade (SSOT) para todo tipo de domínio (Client, Alert, Campaign, KPI de negócio, contratos de hook UseXResult). Barrels em src/types/*.ts (client.ts, alert.ts, metaAds.ts) só reexportam — nunca declaram tipo novo. Componentes de tela e componentes comuns deveriam importar sempre de lá, nunca redeclarar localmente.
Esta consolidação (22/07/2026) une o protótipo navegável com uma auditoria forense real: npx tsc --noEmit rodado sobre a árvore inteira, cross-referenciado contra orbit.ts v1.9.0, mais o log de build/runtime que você colou nas sessões anteriores.
Atualização 11/08/2026: duas sessões adicionais (auditoria do pipeline de ingestão e reconciliação de enums DB↔TS) geraram os itens ORB-DEBT-020 a ORB-DEBT-034 em ORBIT_GOVERNANCE.md, com o detalhamento forense em LEDGER_REGISTROS.md (documento companion novo, mesmo papel que este HTML tem para as telas — ver ADR-006). As anotações dessas duas sessões foram inseridas nos painéis de Modo Auditoria das telas afetadas abaixo, sempre citando o ID exato do achado.

Supabase (orbit.*) │ query tipada ▼ repository (retorna orbit.ts type) │ ▼ hook (useClients/useAlerts/useMetaAds) │ retorna FLAT: { campaigns, kpis, status, error, refetch } │ ou { alerts, status, error, refetch } ▼ screen (interface local UseXResult) │ ESPERA um shape diferente do que o hook entrega │ ex.: espera `{ data: {...}, status, error }` │ ex.: espera `{ alerts }`, hook devolve `{ data }` ▼ componente comum (ClientCard/AlertCard/CampaignRow) │ tem SEU PRÓPRIO tipo local (Client/Alert/Campaign) │ divergente do que a screen envia ▼ ❌ build quebra (Carteira) ou ⚠ fallback silencioso renderiza vazio sem erro visível (Alertas/MetaAds)
Fluxo de dados — TO BE (alvo)
Supabase (orbit.*) │ ▼ repository (retorna orbit.ts type) │ ▼ hook — retorna exatamente o shape de UseXResult tal como definido em orbit.ts (mesmo nome de campo, mesma forma) ▼ screen — importa UseXResult de orbit.ts, NÃO redeclara a interface localmente ▼ componente comum — importa Client/Alert/ Campaign/KPI de orbit.ts (via barrel), NÃO redeclara localmente ▼ ✅ um único contrato, ponta a ponta — qualquer mudança em orbit.ts propaga e o tsc acusa em COMPILAÇÃO, não em produção
Convenção de cor — Semaphore unificado Decisão 22/07/2026
Antes desta rodada, o código real tinha 9 tipos de status/cor diferentes (AlertSeverity, ClientHealthStatus, AlignmentStatus, StatusVariant, SemaphoreColor, GlowColor, TrendColor, AlignmentColor, MetaAdsKPIStatus) resolvendo pra 3 paletas visuais divergentes — incluindo um bug confirmado onde SemaphoreColor.verde mapeava para GlowColor.cyan (o nome mentia sobre a cor) e um componente morto (AlignmentBar.tsx singular, removido) com Tailwind cru desacoplado de qualquer token.
Decisão: paleta neon (cyan/gold/red) como padrão único daqui pra frente, servida por um componente Semaphore.tsx unificado (substitui o antigo Semaphore.tsx + SemaphoreIndicator.tsx), usando ClientHealthStatus (healthy · warning · critical · unknown) como vocabulário canônico — os demais tipos de status devem migrar para ele ou mapear explicitamente via uma ponte nomeada (como o TREND_COLOR_MAP que já existe em orbit.ts, mas cujo uso não foi propagado a todos os repositórios).
Este protótipo já reflete a decisão nas telas que representam esses componentes ao vivo: semáforo de saúde (Carteira), AlignmentBars (Avatar Alignment) e KPICard/GlowingNumber/DeltaText (Overview IG, Meta Ads, Google Ads). Os tons de badge genéricos usados no Relatório (client-facing) e nas tabelas de Meta Ads/Criativos ligadas a MetaAdsKPIStatus (tipo hoje morto, tela sem rota) foram mantidos como estavam — são um sistema visual separado, não coberto por esta decisão.
